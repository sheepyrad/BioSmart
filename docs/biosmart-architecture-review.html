BioSmart — Architecture Review & Overhaul Plan

A deep reflection on cgflow (Python engine) and cgflow-gui (Electron/React frontend), with the goal of making BioSmart installable and usable by non-technical scientists.

Diagnosis. BioSmart is a research pipeline with a developer console bolted on. The engine assumes a Linux GPU workstation hand-configured with three conda environments, weights fetched from Google Drive and Hugging Face, an Enamine-derived Building-block library (today env_dir) that is not in the repo, and absolute paths from the author's machine baked into example configs. The GUI assumes it is running from the monorepo checkout next to ../cgflow with conda on PATH, and it cannot be packaged as-is. Nothing in the system checks whether the machine is actually ready before a user hits Start.

The central architectural mistake is that the two halves are coupled at the filesystem level (sibling directories, __dirname tricks, BFS scans of cgflow's output tree, regex parsing of log lines, a Zod schema that shadows a Python dataclass) while being decoupled at the level that matters: neither side owns the contract for "what is a run, what is its config, what is its state".

Recommended direction (bold, no backward compatibility):
  1. Ship the engine as one container image (all Python envs baked in via micromamba/pixi, weights fetched by an in-image biosmart assets sync). The scientist’s install is that image. Lab 3090s develop and validate with pixi from the same lockfile.
  2. Move the runner into Python (FastAPI inside the engine). It already spawns Python and reads SQLite; a Python server does that natively. Delete runner.ts, main.ts IPC handlers, and sql.js.
  3. Drop Electron and Bun from the deployment story. The UI becomes a static Vite build. In v1 the host serves it on 127.0.0.1. In v2 the host also serves it on its Tailscale address, and a worker install has no UI (ADR-0006).
  4. One canonical schema, generated once. A pydantic RunSpec in Python exports JSON Schema and TypeScript types; the UI form and the YAML written to disk are both derived from it.
  5. Structured events instead of regex. The trainer emits JSONL progress events and writes a run.json manifest; the API no longer guesses where Boltz put a CIF.
  6. Replace the config form with a 3-step wizard + presets and a Doctor screen that refuses to start until GPU, environments, weights and a Building-block library are all green.

cgflow (engine)

  • ~60k LOC under src/: cgflow 18.5k, FlashBind 18.1k (vendored), gflownet 10.5k (vendored fork), synthflow 7.8k, rxnflow 4.8k (namespace pkg, no __init__).
  • Entry points are scripts that sys.path.insert src/; pyproject.toml has no [project.scripts].
  • Config: argparse → OmegaConf → nested dataclasses via init_empty; ~65 *Config classes; no exported schema.
  • Resume exists only for Boltz; SIGINT cleanup exists only for Boltz.

cgflow-gui (frontend)

  • ~6k LOC renderer + 3.6k LOC Electron/runner. ConfigBuilder.tsx 1,299, Dashboard.tsx 1,033.
  • HTTP runner is the live path; IPC run handlers in main.ts are a stale ~400 LOC duplicate.
  • No onboarding, no environment check, no tests, no lint, no CI; toasts/framer-motion/3 components unused.
  • electron-builder packs only dist/ + dist-electron/; a packaged app cannot find cgflow or conda.

Glue & assets

  • Conda bridging via synthflow/utils/conda_env.py: locates conda base heuristically, runs conda run --no-capture-output -n ….
  • Assets: pose ckpt (gdown), FABind+ 360 MB + FlashBind 250 MB (HF, scripted), ESM3 (gated HF), Boltz cache (multi-GB, first use), env_dir (user builds from Enamine SDF).
  • Hard-coded /media/data/conrad_hku/… in shipped configs and GUI defaults (hf_cache).

02Friction inventory — what a new user must do today

Reconstructed from README.md, cgflow/README.md, cgflow/data/README.md, src/FlashBind/env.yaml, FABind_plus/README.md, and GUI docs. Steps marked trap have a documented or observed way to silently go wrong.

  1. Obtain a Linux x86_64 machine with an NVIDIA GPU; check glibc (20.04 → torch 2.6/cu124; 22.04+ → 2.9/cu126; flashaffinity needs ≥2.33). trap
  2. Install git, git-lfs (for upstream FABind path), mamba/conda, CUDA driver, gcc (needed at runtime to build the iJIT LD_PRELOAD stub for fabind).
  3. git clone --recurse-submodules; verify submodule is on the right branch (README says feat/flashbind-integration, status says drug-pipeline-v1). trap
  4. Create env cgflow: choose torch pin by OS, install PyG wheels from the matching index, pip install -e . (pulls 2 git+https deps), install Boltz with a constraints file so pip does not upgrade torch. trap
  5. Discover medchem is imported but not declared; install it manually. trap
  6. Create env flashaffinity from a 250-line env.yaml with order-sensitive pip installs (torch before flash-attn), cuequivariance CUDA ops, mmseqs2, ray.
  7. Create env fabind (Python 3.8, torch 1.12/cu113, graph-tool, torchdrug, rdkit 2021) — a 2022-era stack that increasingly does not resolve on modern conda channels. trap
  8. Run ./scripts/setup-cgflow-assets.sh for FABind+/FlashBind checkpoints (≈610 MB).
  9. gdown the CGFlow pose checkpoint from Google Drive into cgflow/weights/ (Drive rate limits; no checksum).
  10. Accept the ESM3 license on Hugging Face, create a token, huggingface-cli login inside the flashaffinity env. trap
  11. Set hf_cache/HF_HOME to a big disk; edit shipped YAML that points at /media/data/conrad_hku/hf_cache. trap
  12. Download an Enamine building-block SDF (requires Enamine account), run a_stock_to_smi.py → optional b_druglike_filter.py → c_create_env.py (CPU-hours) to produce data/envs/…. trap
  13. Let boltz predict download its model + CCD cache on first oracle call (multi-GB, mid-run). trap
  14. Prepare inputs: PDB, optional reference ligand .mol2, MSA .a3m (or enable MSA server), for FlashBind a prot.json and a PDB whose stem equals protein_id with no underscores. trap
  15. Install Bun (or Node 18+), cd cgflow-gui && bun install (downloads Electron).
  16. Create cgflow-gui/.env.local with CGFLOW_ALLOWED_WORKSPACE_PATHS if data lives outside $HOME. trap
  17. bun run electron:dev (or dev:web), keep the terminal open; handle "Port 45733 in use" with fuser -k.
  18. In the UI, type absolute paths for PDB, MSA, result dir, env dir (web mode has no pickers). Hidden defaults still point to ./weights/cgflow_crossdock.ckpt and ./data/envs/enamine_stock_new. trap
  19. Click Start. If anything above is wrong, read the red log box.
Time to first run for a new lab member: realistically 1–3 days with help, unbounded without. Nine of nineteen steps have silent failure modes. None of this is the science.

3.3 Code quality snapshot

Python (cgflow)

  • 13 files > 800 LOC; scripts/opt/tasks/boltz.py is 1,071 LOC and holds oracle, cache, resume, logging, process-group management.
  • Five near-copy opt entry points (opt_boltz, opt_flashbind, opt_unidock, opt_vina, opt_unidock_boltzina); build_training_data_loader duplicated.
  • ~118 TODO/FIXME/HACK; ~236 print( vs ~72 logger calls in the opt/synthflow scope.
  • Ruff configured but pre-commit only gates scripts/ with --exit-zero; 12 test files, one real unittest, no pytest config.
  • Committed blob: FABind_plus/inference_examples/…/processed_protein.pt 12 MB; inference_examples/ 14 MB total; experimental/ 4 MB scratch.
  • Undeclared runtime import medchem; git+https deps for druglikeness, pharmaconet.

TypeScript (cgflow-gui)

  • runner.ts 2,345 LOC: HTTP routing, SSE, YAML generation, PDB→sequence, sql.js, filesystem allowlists, run registry, artifact scanning in one file.
  • ~350–450 LOC duplicated between main.ts IPC and runner.ts (spawn, DB, complex lookup) with divergent behaviour.
  • State is useState sprawl across two 1k-line pages; no store, no toasts wired despite the dependency.
  • Unused: MoleculeCard, ReactionPathway, SmilesCell, framer-motion, 7 Radix packages.
  • RDKit WASM is loaded from unpkg.com at runtime → the "offline desktop app" needs internet.
  • Security: no auth on :45731; runner can read any file under $HOME; IPC file handlers have no allowlist at all.
  • No ESLint, no tests, no CI, no release/ artefact ever built.

3.4 What is actually good and should be kept

  • The science core: CGFlow pose model + RxnFlow synthesis GFN + pluggable oracle tasks (BaseDockingTask seam) is a sound design and already engine-agnostic at the trainer level.
  • The HTTP+SSE runner model (as opposed to IPC) was the right call; only its language and location are wrong.
  • Mol* residue picking, the parallel-coordinates filter, and the ECharts metrics are genuinely useful UI and should be lifted into the new shell largely unchanged.
  • HF-based asset download with a shell wrapper (download_flashbind_assets.sh) is the right pattern; it needs to be generalised, not replaced.
  • pathSecurity.ts shows the right instinct; it just belongs on the server side, in Python.

04Design principles for the overhaul

1. One machine, one artefact

The GPU box gets exactly one thing installed: a container image (or one pixi workspace). Everything else—Python, torch × 3, weights, building blocks—lives inside it or is pulled by it.

2. Python owns the run

Config schema, run registry, progress events, artefact manifest, and process supervision live in the language that already runs the science. The UI is a pure client.

3. Browser is the client

Scientists use whatever laptop they have. A URL on the lab network beats a DMG that has to ssh to a Linux box anyway.

4. Green before Start

A Doctor check (GPU, VRAM, disk, environments, weights, Building-block library, HF token) gates the Start button and offers one-click fixes.

5. Derive, don't duplicate

JSON Schema, TS types, the form, the YAML on disk and the CLI flags are all generated from a single pydantic model.

6. Presets over parameters

Default experience is: upload PDB → click residues → pick “Quick / Standard / Thorough” → Start. Everything else sits behind an “Advanced” disclosure.

06Proposals (as agreed)

Ranked by impact on the stated goal. Tags: bold = structural change, quick = a local change. Every item below reflects the consensus in §0.5; the load-bearing ones are ADRs. There is no schedule.

P1 · One container image; host prerequisites are "driver + Docker" bold ADR-0001

Bake four Python environments into a single image built from one pixi.lock: server (FastAPI, RDKit, no torch), default (cgflow + Boltz-2), flashaffinity, fabind. Environments are addressed by interpreter path (/envs/<env>/bin/python); conda_env.py's base-discovery heuristics and the runtime-compiled iJIT stub go away (the stub, if still needed by torch 1.12, is built once at image build). compose.yaml: one service, GPU reservation, runs as the invoking user, restart: unless-stopped, mounts for the Runs root, assets and ~/BioSmart/inputs. install.sh [--with-docker] installs Docker + NVIDIA Container Toolkit on Ubuntu via sudo, otherwise prints the commands; then pulls, drops a desktop launcher, and opens http://127.0.0.1:8000. Images published to GHCR from CI. On the lab 3090s the same lockfile is installed with pixi and used for validation. v2 chooses host or worker at install (ADR-0006); a worker does not serve the UI.

Expected image size: 18–25 GB (three CUDA torch stacks). Accepted as a one-time pull. Weights are not baked in; they land in the assets mount via P3. Lab machines use pixi install from the same lockfile.

P2 · The runner is Python: FastAPI server in the image, TypeScript backend deleted bold ADR-0002

The server runs in the server environment with a single uvicorn worker; the supervisor and FIFO GPU queue are in-process asyncio tasks with durable state in the registry. It spawns the engine as a subprocess in the same container (start_new_session=True, pgid + heartbeat recorded, reattach on restart by tailing events.jsonl). Events reach the browser over Server-Sent Events; commands are REST. Deleted: runner.ts (2,345), main.ts (749), preload.*, flashbindAdapter.ts, pathSecurity.ts, webFallback.ts, useIpc.ts, sql.js, electron, electron-builder, vite-plugin-electron, concurrently, wait-on. Net ≈4,000 LOC removed; one runtime instead of three.

P3 · Asset manager with a checksummed registry quick

One assets/registry.yaml lists every downloadable artefact: CGFlow Pose model (mirrored from Google Drive to a BioSmart Hugging Face organisation, with sha256), FABind+ and FlashBind checkpoints, Boltz-2 weights + CCD (pre-warmed by the Doctor instead of downloaded mid-Run), and ESM3 (gated: the Doctor asks for a Hugging Face token once and stores it in the assets mount). biosmart assets sync [--only …] is idempotent, resumable, shows progress, verifies checksums, and is what the Doctor "Fix" button calls. Building-block libraries are not assets: they are built in-app (P6).

P4 · Single canonical RunSpec in pydantic; generate everything else bold ADR-0002

Replace the argparse → OmegaConf → dataclass chain with a pydantic v2 model tree: RunSpec{target, pocket, budget, scorer: Boltz2Spec|FlashBindSpec, library_id, advanced}. Export JSON Schema (biosmart export-schema), generate TS types from OpenAPI (openapi-typescript), fail CI on drift. The engine consumes the same JSON the UI posted; the YAML on disk is an output for provenance, never an input users edit. Machine plumbing (checkpoint paths, interpreter paths, caches) lives in server Settings, not in the spec.

P7 · Dissolve the submodule; hygiene pass quick

  • Import cgflow into the monorepo with history; no upstream sync. Leave experiments/, experimental/, pretraining/multi-pocket scripts, and wandb unmodified. Remove Boltzina only (tasks, utils, configs, script). UniDock/Vina code stays for parity with tsa87/cgflow.
  • Declare medchem; pin druglikeness/pharmaconet by commit; add [tool.setuptools.packages.find] and an __init__.py for rxnflow.
  • Strip every /media/…, /home/… path; example configs become Presets in code.
  • Ruff + mypy (gradual) on src/; pytest with a CPU end-to-end Run using a FakeScorer; ESLint + tsc + vitest on web; image build on tag.

P8 · Job supervision done properly quick

In-process supervisor in the single uvicorn worker: spawn with start_new_session=True, record pid + pgid + heartbeat in the registry, reattach on server restart, kill by process group, one Run on the GPU at a time with a FIFO queue (cancel allowed). Container runs as the invoking user so Run folders on the user's disk or network drive are owned by them.

P9 · Persistent Scorer workers and a formal Scorer interface bold ADR-0005

Today every Scoring round launches fresh processes and reloads models: FABind+ three scripts, FlashBind two predict.py calls, Boltz-2 one boltz predict per Candidate. The engine instead starts one long-lived worker per environment at Run start (models loaded once, JSON-lines over stdin/stdout, dies with the Run); Boltz-2 becomes a resident worker predicting in batches via Boltz's Python entry point. Interface: Scorer.prepare(target, pocket) → context_hash, Scorer.score(round_no, candidates) → ScoreResult[], Scorer.flush(); FlashBind composes a PoseProvider (FABind+ default; CGFlow Pose model as a lowest-priority alternative). Environment consolidation (porting FABind+, aligning torch pins) is not planned: FABind+'s speed is the reason FlashBind exists.

P10 · Security defaults for a solo workstation quick

v1 binds 127.0.0.1 only; no token. Uploads and the mounted ~/BioSmart/inputs folder instead of arbitrary path reads; artefact reads confined to the Runs root. v2 (ADR-0006) adds a Tailscale listener on the host and a worker role with no UI. Trust is tailnet membership, not a LAN token.

Considered and not chosen

  • Fixing Electron packaging (extraResources + bundled conda): still requires host conda/CUDA management; multiplies installer variants.
  • Rewriting the science code: no user-facing benefit; risk of changing results. Wrap it, don't rewrite it.
  • Separate worker container or long-lived engine daemon: defers cleanly; the server↔engine boundary (spec, events, Run folder) makes it a compose change later.
  • Postgres, per-user auth, public LAN bind, HPC/Apptainer: not in v1. v2 remote access is the tailnet host/worker split in ADR-0006, not a tokenised LAN server.
  • Server-rendered UI (HTMX) or a fresh SPA: would discard Mol*, ECharts and RDKit.js work that is the reason a browser client is right.
  • Demo or prebuilt Building-block library: the scientist builds their own from their Enamine file; the Doctor self-test is a --dry-run.

07Roadmap (as agreed)

Solo developer. Phases are a dependency order. Each phase leaves the system usable. There is no schedule. Engine CLI and server are built together on the same spec, supervisor and event reader; UI last, generated from the schema. v2 (ADR-0006) comes after this sequence.

Phase 0 — Hygiene
  • Dissolve submodule. Leave experiments, experimental, pretraining, multi-pocket scripts, and wandb unmodified. Remove Boltzina only. Declare medchem; pin git deps; fix rxnflow packaging; strip absolute paths; ruff/pytest/tsc/eslint CI (P7).
  • pixi.toml with four environments and a lockfile that installs on Ubuntu 22.04; replace conda run with interpreter paths (P1).
  • Done when: fresh clone → pixi install → the NS5 Boltz-2 config runs headless.
Phase 1 — Engine + server core
  • pydantic RunSpec + Presets; biosmart CLI; JSONL events; Run folder + Run database; SIGTERM checkpoint/resume for both Scorers; provenance (P4, P5).
  • Scorer / PoseProvider interface; persistent workers for fabind, flashaffinity and Boltz-2; global Scorer cache (P9, ADR-0004, ADR-0005). FakeScorer for CI.
  • Doctor; assets registry + sync (Pose model mirrored to HF); Library build job (P3, P6).
  • FastAPI server in the server env: registry, FIFO queue, in-process supervisor with reattach, Index ingest with descriptors and fingerprints, SSE, static SPA (P2, P8).
  • Done when: Doctor is green on the lab box; a Run started from the API streams events, survives a server restart, resumes after Stop; the CPU end-to-end test passes in CI.
Phase 2 — Image + installer
  • Dockerfile from pixi.lock; compose.yaml (runs as user, restart policy, mounts); install.sh [--with-docker]; desktop launcher; GHCR publish (P1).

Phase 4 — Low-priority tail

Target end state: a scientist runs one script on their GPU workstation, builds a Building-block library once from their Enamine file, and opens http://127.0.0.1:8000 from the desktop launcher. First Run: upload PDB, click six residues, choose “Standard”, press Start. No terminal, no YAML, no paths. In v2 they can open the host’s tailnet URL from their own computer.

08Storage model (agreed)

Design goal: a Run folder is fully interpretable on its own; the server adds cross-Run capabilities without ever becoming the source of truth. See ADR-0003, ADR-0004.

Registry (biosmart.sqlite, server-owned)

  • runs, run_queue, libraries, targets, settings, doctor_results
  • scorer_cache(scorer, scorer_version, context_hash, canonical_smiles, scores_json, artifact_ref) — context_hash = Target file hash + Pocket definition + MSA hash
  • Index (derived, rebuildable): candidate_index(run_id, candidate_id, canonical_smiles, inchikey, status, best_score, …), candidate_props(mw, logp, hbd, hba, tpsa, qed, sa, rings, lilly, pains, …), candidate_fp(morgan2048)

Run database (run.sqlite, engine-owned, one per Run)

  • meta(schema_version, …)
  • candidates(id, iteration, round_no, canonical_smiles, status ∈ {scored, filtered, failed}, failure_reason, reward, route_json, pose_ref, temperature)
  • scores(candidate_id, scorer, affinity_*, probability_*, raw_json)
  • scoring_rounds(round_no, scorer, n_sent, n_ok, n_failed, secs, gpu_mem_peak) — feeds Preset ETAs
  • iterations(iteration, loss, reward_avg, top10, top100, top1000, temperature_lo, temperature_hi, n_valid, secs, …) — every key the trainer logs today
  • artifacts(candidate_id, kind, path)

Run folder

<Runs root>/<run_id>/
├── spec.json  run.json  provenance.json  events.jsonl  run.sqlite
├── target/            # copied Target file + Pocket definition
├── library.json       # name, source, created-at, block count, hash
├── checkpoints/
├── poses/round_{N}.sdf
└── scorer/round_{N}/  # all Scorer working files, retained in full
  • Descriptors and fingerprints are computed once by the server at ingest; v1 search = substructure (RDKit over one Run) + similarity (Morgan in the Index). Scaffold grouping and relational route analytics later; routes are JSON blobs in v1.
  • Failed and filtered Candidates are stored with a reason.
  • "Import Run" rebuilds the Index from a folder; "Archive Run" produces one .tar.zst.
  • Open verification (later): whether Boltz-2's per-Candidate Target/MSA processing can be computed once per Run and shared, which would remove most Scorer working-file volume (today ≈1–3 MB per Candidate, 60–200 GB per 64k-Candidate Run).

A4 · GUI runner facts
  • Spawn: spawn('conda', ['run','--no-capture-output','-n', CGFLOW_CONDA_ENV, 'python', opt_*.py, '--config', …, '--result_dir', …, '--env_dir', …], {cwd: CGFLOW_ROOT}).
